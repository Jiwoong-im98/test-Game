사무동은 정상 가동 중입니다. 이번 보고는 두 가지를 다룹니다 — 클로드 코드를 운영하는 방법과, 사업·업무 방향에 대한 제언입니다. 아직 도구가 손에 익지 않은 것은 자연스러운 과정이니 조급해할 필요는 없습니다.

SECTION A

클로드 코드 운영 가이드

coder범위 내 구현

오늘은 2026년 9월 15일, 이번 사무동 운영 보고서를 처음 갱신하는 시점입니다. 어제(9월 14일) 이미 네 차례에 걸쳐 같은 절차로 저장소 구성을 점검한 바 있는데, 오늘 다시 .claude 폴더 전체를 처음부터 끝까지 다시 열어 확인해 본 결과 구성에는 변화가 없었습니다. 즉 아래 내용은 오늘 이 시각 기준으로 실제 파일을 직접 읽고 확인한 것이며, 지어낸 설명이 아닙니다. 클로드 코드를 이제 막 시작하신 분이라면 이 섹션부터 천천히 따라 읽으시면 지금 이 저장소가 어떻게 짜여 있는지 감을 잡으실 수 있습니다.

가장 먼저 볼 것은 .claude/agents 폴더입니다. 이 안에는 README.md 한 장과 실제 서브에이전트 정의 여섯 개(coder, debugger, doc-updater, planner, reviewer, tester)가 들어 있습니다. planner는 읽기 전용으로만 동작하며 코드를 한 줄도 고치지 않고, 작업을 구체적인 단계별 계획으로 쪼개는 일만 합니다. coder는 그 계획 중 한 단계, 또는 명확히 좁혀진 작업 하나만 실제로 구현하고 스스로 범위를 넓히지 않도록 설계돼 있습니다. tester는 구현이 끝난 뒤 실제로 명령을 실행해서 통과·실패를 직접 확인하고 근거를 남기는 역할이며, 확인 없이 "될 것 같다"고 보고하지 않는 것이 원칙입니다. reviewer는 코드를 고치지는 않지만 정확성·중복·효율성 관점에서 다시 한번 읽고 문제를 지적합니다. debugger는 테스트가 실패하거나 에러가 났을 때 먼저 재현부터 하고, 추측으로 고치는 대신 근본 원인을 찾아 최소한의 수정만 적용합니다. doc-updater는 코드가 바뀐 뒤 CLAUDE.md나 README.md가 실제 상태와 어긋나지 않도록 정리하는 역할이며, 없는 내용을 새로 지어 쓰지는 않습니다.

이 여섯 역할을 한 번에 순서대로 지휘하는 명령이 .claude/commands/orchestrate.md에 정의된 /orchestrate입니다. 이 명령을 실행하면 메인 에이전트가 오케스트레이터가 되어 planner로 계획을 세우고, 각 단계를 coder에게 하나씩 맡기고, 끝날 때마다 tester로 검증하며, 문제가 반복되면 debugger로 전환해 근본 원인을 분석하고, 전체 구현이 끝나면 reviewer로 마지막 점검을 합니다. 다만 이 파이프라인이 커밋이나 푸시처럼 되돌리기 어려운 작업까지 자동으로 진행하지는 않으며, 그런 지점에서는 반드시 사용자에게 다시 확인을 구하도록 돼 있습니다. 간단한 질문이나 몇 줄짜리 수정에까지 이 여섯 단계를 다 부르면 오히려 시간이 더 걸리니, 평소에는 필요한 부분만 골라 쓰시는 편이 낫습니다.

.claude/commands 폴더에는 이 밖에도 네 개의 짧은 명령이 더 있습니다. /commit은 git status와 diff를 먼저 확인하고 의미 단위로 커밋 메시지를 작성해 주며, 비밀키로 보이는 파일이 스테이징돼 있으면 미리 알려줍니다. /catchup은 최근 커밋과 변경 내역을 읽고 지금 이 프로젝트가 어떤 상태인지 요약해 주는 명령이라, 며칠 만에 다시 돌아오셨을 때 가장 먼저 써 보시면 좋습니다. /todos는 코드베이스 전체에서 TODO·FIXME·HACK 주석을 찾아 목록으로 정리해 주고, /pr-description은 현재 브랜치와 기본 브랜치의 차이를 바탕으로 PR 제목과 설명 초안을 써 줍니다. 이 네 명령은 모두 코드를 직접 고치지 않고 확인·요약·정리만 하는 안전한 명령이라는 공통점이 있습니다.

위험도가 더 높은 작업을 위한 장치도 마련돼 있습니다. .claude/skills/cross-verify/SKILL.md에는 배포, 데이터베이스 마이그레이션, 삭제나 되돌리기 힘든 작업, 보안·인증 관련 코드처럼 실패 비용이 큰 변경을 다른 세션에게 독립적으로 다시 검토받는 절차가 정의돼 있습니다. 이 스킬은 SKILL.md 안에 disable-model-invocation: true가 명시돼 있어서, 다른 세션에 메시지를 보내는 부작용이 있는 만큼 클로드가 스스로 판단해서 자동으로 실행하지 못하고 사용자가 직접 /cross-verify라고 불러야만 움직입니다. 절차도 신중하게 짜여 있는데, 먼저 정말 2세션 검증이 필요한 수준인지 스스로 판단하고, ListAgents로 열려 있는 다른 세션이 있는지 확인한 뒤, 있으면 원본 코드를 통째로 복사하지 않고 파일 경로와 변경 요지만 요약해 보내 독립적인 검증을 요청합니다. 다른 세션이 없으면 교차검증이 불가능하다고 솔직히 알리고 대신 reviewer 서브에이전트로 검증한 결과를 보고합니다. 평소 변경에는 reviewer 서브에이전트만으로 충분하고, 정말 필요한 순간에만 이 스킬을 쓰시라고 안내가 돼 있습니다.

.claude/settings.json도 오늘 다시 확인했습니다. 허용 목록에는 git status·diff·log·show·branch·remote -v·fetch·stash list처럼 읽기 전용에 가까운 git 명령과, npm·yarn·pnpm·pip의 설치·실행·테스트 명령, pytest, python/node 버전 확인 명령이 올라가 있어서 이런 명령은 매번 승인받지 않고 바로 실행됩니다. 반대로 차단 목록에는 rm -rf, git push --force, git reset --hard, git clean -f 네 가지가 올라 있어서, 이 명령들은 아무리 요청해도 이 설정 안에서는 실행되지 않습니다. 초보자 입장에서는 이 목록을 외우실 필요는 없고, "되돌리기 쉬운 일은 편하게, 되돌리기 어려운 일은 항상 한 번 더 확인"이라는 원칙만 기억해 두시면 충분합니다.

마지막으로 CLAUDE.md는 오늘도 프로젝트 개요·구조·개발 명령어·컨벤션 네 항목이 모두 "작성 예정"으로 비어 있는 상태 그대로였습니다. 이 파일은 클로드 코드가 매번 작업을 시작할 때 함께 읽는 안내문 같은 역할을 하기 때문에, 짧게라도 몇 줄 채워 두시면 다음 대화에서 매번 같은 설명을 반복하지 않아도 되어 훨씬 편해집니다. 오늘 당장이 아니어도 괜찮으니, 여유가 생기실 때 한 항목씩 채워 나가시길 권해 드립니다.

SECTION B

사업·업무 방향 메모

docs/advice/context.md 파일을 오늘도 다시 열어 봤지만 "현재 상황", "최근 고민", "최근 결정/변화" 세 항목이 모두 어제와 똑같이 "작성 예정"으로 비어 있었습니다. 그래서 오늘도 지어낸 일반론 대신, harness_test 저장소에 실제로 남아 있는 최근 커밋 15개를 근거로 말씀드리겠습니다. 어제 커밋에 오늘 새벽(UTC 기준 9월 14일, 서울 시간으로는 이미 9월 15일에 걸친) R4 갱신 커밋까지 더해서 보면, 최근 며칠 사이 어떤 순서로 일해 오셨는지가 더 또렷하게 드러납니다.

첫째, 시작을 작게 잡으셨습니다. 9월 8일 커밋 로그를 보면 "초기 하네스 스캐폴드를 재사용 가능한 시작 템플릿으로 재구성 — .claude/CLAUDE.md를 루트로 옮기고 기본 권한 허용목록 추가"로 시작합니다. 처음부터 완성된 설계를 그리지 않고, 최소한의 뼈대만 세운 뒤 재사용 가능한 형태로 다듬어 가신 것입니다. 사업도 마찬가지입니다. 처음 며칠은 "이 구조가 다음에도 그대로 쓸 수 있는가"를 점검하는 데 쓰는 편이, 나중에 통째로 뜯어고치는 비용보다 훨씬 쌉니다.

둘째, 역할을 미리 나눠 두셨습니다. 같은 날(9월 8일) "공용 서브에이전트 추가: reviewer, debugger, doc-updater"와 "공용 슬래시 커맨드 추가: /commit, /catchup, /todos, /pr-description" 커밋이 이어졌고, 이틀 뒤인 9월 10일에는 "오케스트레이션 파이프라인 추가: planner/coder/tester 서브에이전트 + /orchestrate 명령"과 "고위험 변경의 교차검증을 위한 /cross-verify 스킬 추가"가 같은 시각(21시 46~47분)에 잇달아 올라갔습니다. 계획하는 역할과 구현하는 역할, 검증하는 역할을 처음부터 분리해 둔 것인데, 이는 실제 팀을 꾸릴 때도 그대로 옮겨 쓸 수 있는 원칙입니다. 특히 위험도가 큰 결정일수록 검증 절차를 별도로, 더 무겁게 마련해 둔 점이 눈에 띕니다 — 사업에서도 계약, 채용, 큰 지출처럼 되돌리기 어려운 결정에는 이런 식의 "한 단계 더 확인하는 절차"를 미리 정해 두시길 권해 드립니다.

셋째, 시도했다가 과감히 되돌리는 것을 주저하지 않으셨습니다. 9월 13일 커밋을 순서대로 보면 "제갈량 스타일의 클로드 코드·사업 조언 메모리얼 페이지 추가"(16:00) → "다른 컴퓨터에서 조언 팝업을 켤 수 있는 설치 스크립트 추가"(16:04) → "초원 사슴 삽화 추가"(21:05) → "조언 페이지를 통합된 '사슴 대장' 초원 저널로 리디자인"(21:21) → "손으로 그린 사슴 삽화 제거"(21:52)로 이어집니다. 콘셉트를 잡고, 다른 컴퓨터에서도 쓸 수 있게 이식하고, 요소를 더해 보고, 통째로 다시 디자인하고, 마음에 들지 않는 부분은 결국 빼내는 과정을 하루 안에 다 거치신 것입니다. 이건 실패가 아니라 정상적인 반복 작업입니다. 사업 아이디어나 제품 방향도 이렇게 "일단 만들어 보고, 다시 짜고, 안 맞는 건 빼는" 주기를 짧게 여러 번 도는 편이, 처음부터 완벽한 하나를 오래 붙잡고 있는 것보다 결과적으로 더 빨리 원하는 형태에 도달합니다. 다만 이런 반복이 편했던 건 매번 git으로 기록을 남겨 두셨기 때문이라는 점도 함께 짚어드리고 싶습니다 — 되돌릴 수 있다는 안전망이 있어야 과감한 시도도 부담 없이 할 수 있습니다.

넷째, 어제(9월 14일) 하루 동안 이 보고서 자체를 네 번 고쳐 오셨습니다. 다섯째, 그런데 정작 그 파일은 아직 비어 있습니다. context.md를 만드신 지 벌써 하루가 지났는데도 "현재 상황·최근 고민·최근 결정" 세 항목이 모두 "작성 예정" 그대로입니다. 그 결과 Section B는 오늘도 실제 사업 맥락이 아니라 harness_test 저장소의 git 커밋 로그를 근거로 쓰이고 있습니다. 도구를 만들어 두는 것과 그 도구를 실제로 채워 쓰는 것 사이에는 언제나 하루이틀의 간극이 생기기 마련이지만, 이 간극이 길어지면 애써 만든 자동화가 절반만 작동하는 상태로 굳어 버릴 수 있습니다. 오늘 드리고 싶은 가장 구체적인 제안은 이것입니다 — 지금 당장 context.md를 열어 딱 세 줄만 채워 보시길 권해 드립니다. 지금 어떤 사업/일을 하고 계신지 한 줄, 요즘 가장 크게 고민하는 것 한 줄, 최근에 내린 결정이나 바뀐 것 한 줄이면 충분합니다. 내일부터는 이 보고서가 실제 사업 맥락을 근거로 훨씬 구체적인 조언을 드릴 수 있게 됩니다.
