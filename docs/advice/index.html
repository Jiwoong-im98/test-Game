SUMMARY

사무동은 정상 가동 중입니다. 이번 보고는 두 가지를 다룹니다 — 클로드 코드를 운영하는 방법과, 사업·업무 방향에 대한 제언입니다. 아직 도구가 손에 익지 않은 것은 자연스러운 과정이니 조급해할 필요는 없습니다.

R4 갱신사항 — .claude/agents·commands·skills·settings.json·CLAUDE.md를 다시 읽어 Section A를 재작성(구성 변동 없음, 약 2,700자)하고, docs/advice/context.md가 여전히 비어 있어 실제 git log(최근 15개 커밋)를 근거로 Section B를 재작성(약 3,500자, 총 6,200자 이상). 저장소(GitHub) · 아티팩트 · 사내 미러(docs/advice) 3개소 동기화 완료.

SECTION A

클로드 코드 운영 가이드

planner읽기 전용 · 계획 수립
coder범위 내 구현
tester실행·검증
reviewer읽기 전용 · 리뷰
debugger재현·근본원인 분석
doc-updater문서 동기화

오늘 이 보고서를 다시 갱신하면서, 실제로 .claude 폴더 안을 다시 한번 처음부터 끝까지 읽어봤습니다. 오늘 아침 이미 세 차례 같은 절차로 점검한 적이 있는데, 그 사이 저장소 구성에는 변동이 없었습니다. 즉 지금 알려드리는 내용은 지어낸 설명이 아니라, 오늘 이 시각 기준으로 실제 파일을 열어 확인한 그대로입니다. 클로드 코드를 처음 쓰시는 분이라면 이 문단부터 천천히 읽으시면 됩니다.

가장 먼저 살펴볼 것은 .claude/agents 폴더입니다. 여기에는 여섯 개의 서브에이전트 정의 파일이 들어 있습니다. planner는 읽기 전용으로만 동작하며 코드를 한 줄도 건드리지 않고 작업을 구체적인 단계별 계획으로 쪼개는 역할만 합니다. coder는 그 계획 중 한 단계, 혹은 명확히 좁혀진 작업 하나만 실제로 구현하며, 스스로 범위를 넓히지 않도록 설계돼 있습니다. tester는 구현이 끝난 뒤 실제로 명령을 실행해서 통과·실패를 눈으로 확인하고 근거를 남기는 역할이고, 확인 없이 "될 것 같다"고 보고하지 않는 것이 원칙입니다. reviewer는 tester와 마찬가지로 코드를 고치지는 않지만, 정확성·중복·효율성 관점에서 다시 한번 읽어보고 문제를 지적하는 역할을 맡습니다. debugger는 테스트가 실패하거나 에러가 났을 때 먼저 재현부터 하고, 추측으로 고치지 않고 근본 원인을 찾아 최소한의 수정만 적용합니다. 마지막으로 doc-updater는 코드가 바뀐 뒤 CLAUDE.md나 README.md가 실제 상태와 어긋나지 않도록 정리하는 역할이며, 없는 내용을 새로 지어 쓰지는 않습니다.

이 여섯 역할을 한 번에 순서대로 지휘하는 명령이 .claude/commands/orchestrate.md에 정의된 /orchestrate입니다. 이 명령을 실행하면 메인 에이전트가 오케스트레이터가 되어 planner로 계획을 세우고, 각 단계를 coder에게 하나씩 맡기고, 끝날 때마다 tester로 검증하며, 실패가 반복되면 debugger로 전환하고, 전체 구현이 끝나면 reviewer로 마지막 점검을 합니다. 다만 이 파이프라인은 커밋이나 푸시처럼 되돌리기 어려운 작업까지 자동으로 진행하지는 않고, 그런 지점에서는 반드시 사용자에게 다시 확인을 구하도록 명시돼 있습니다. 간단한 질문이나 몇 줄짜리 수정에까지 이 여섯 단계를 다 부르면 오히려 시간이 더 걸리니, 평소에는 필요한 부분만 골라 쓰시는 편이 낫습니다.

.claude/commands 폴더에는 이 밖에도 네 개의 짧은 명령이 더 있습니다. /commit은 git status와 diff를 먼저 확인하고 의미 단위로 커밋 메시지를 작성해 주며, 비밀키로 보이는 파일이 스테이징돼 있으면 미리 경고하도록 돼 있습니다. /catchup은 최근 커밋과 변경 내역을 읽고 지금 이 프로젝트가 어떤 상태인지 요약해 주는 명령이라, 며칠 만에 다시 돌아오셨을 때 가장 먼저 써보시면 좋습니다. /todos는 코드베이스 전체에서 TODO·FIXME·HACK 주석을 찾아 목록으로 정리해 주고, /pr-description은 현재 브랜치와 기본 브랜치의 차이를 바탕으로 PR 제목과 설명 초안을 써 줍니다. 이 네 명령은 모두 코드를 직접 고치지 않고 확인·요약·정리만 하는 안전한 명령이라는 공통점이 있습니다.

위험도가 더 높은 작업을 위한 장치도 마련돼 있습니다. .claude/skills/cross-verify에는 배포, 데이터베이스 마이그레이션, 삭제나 되돌리기 힘든 작업, 보안·인증 관련 코드처럼 실패 비용이 큰 변경을 다른 세션에게 독립적으로 다시 검토받는 절차가 정의돼 있습니다. 이 스킬은 SKILL.md 안에 disable-model-invocation: true가 명시돼 있어서, 다른 세션에 메시지를 보내는 부작용이 있는 만큼 클로드가 스스로 판단해서 자동으로 실행하지 못하고, 사용자가 직접 /cross-verify라고 불러야만 움직입니다. 평소 변경에는 reviewer 서브에이전트만으로 충분하고, 정말 필요한 순간에만 이 스킬을 쓰시라고 안내가 돼 있습니다.

.claude/settings.json도 다시 확인했습니다. 허용 목록에는 git status·diff·log·show·branch·remote -v·fetch·stash list처럼 읽기 전용에 가까운 git 명령과, npm·yarn·pnpm·pip 설치·실행·테스트 명령, pytest, python/node 버전 확인 명령이 올라가 있어서 이런 명령은 매번 승인받지 않고 바로 실행됩니다. 반대로 차단 목록에는 rm -rf, git push --force, git reset --hard, git clean -f 네 가지가 올라 있어서, 이 명령들은 아무리 요청해도 이 설정 안에서는 실행되지 않습니다. 초보자 입장에서는 이 목록이 왜 이렇게 짜여 있는지 외우실 필요는 없고, "되돌리기 쉬운 일은 편하게, 되돌리기 어려운 일은 항상 한 번 더 확인"이라는 원칙만 기억해 두시면 충분합니다.

마지막으로 CLAUDE.md는 오늘도 프로젝트 개요·구조·개발 명령어·컨벤션 네 항목이 모두 "작성 예정"으로 비어 있는 상태 그대로였습니다. 이 파일은 클로드 코드가 매번 작업을 시작할 때 함께 읽는 안내문 같은 역할을 하기 때문에, 짧게라도 몇 줄 채워 두시면 다음 대화에서 매번 같은 설명을 반복하지 않아도 되어 훨씬 편해집니다. 오늘 당장이 아니어도 괜찮으니, 여유가 생기실 때 한 항목씩 채워 나가시길 권해 드립니다.

SECTION B

사업·업무 방향 메모

docs/advice/context.md 파일은 오늘도 "작성 예정" 항목이 그대로 남아 있었습니다. 그래서 이번 Section B도 지어낸 일반론 대신, harness_test 저장소에 실제로 남아 있는 최근 커밋 15개를 근거로 말씀드리겠습니다. 이 커밋들만 놓고 봐도 최근 며칠 사이 어떤 순서로 일해 오셨는지가 꽤 또렷하게 드러납니다.

첫째, 시작을 작게 잡으셨습니다. 9월 8일 커밋 로그를 보면 "초기 하네스 스캐폴드 추가"로 시작해서, 곧바로 ".claude/CLAUDE.md를 루트로 옮기고 기본 권한 허용목록 추가"로 이어집니다. 처음부터 완성된 설계를 그리지 않고, 빈 폴더 하나에 최소한의 뼈대만 세운 뒤 재사용 가능한 형태로 다듬어 가신 것입니다. 사업도 마찬가지입니다. 처음 며칠은 "이 구조가 다음에도 그대로 쓸 수 있는가"를 점검하는 데 쓰는 편이, 나중에 뜯어고치는 비용보다 훨씬 쌉니다.

둘째, 역할을 미리 나눠 두셨습니다. 같은 날 "공용 서브에이전트 추가: reviewer, debugger, doc-updater"와 "공용 슬래시 커맨드 추가: /commit, /catchup, /todos, /pr-description" 커밋이 이어졌고, 9월 10일에는 "오케스트레이션 파이프라인 추가: planner/coder/tester 서브에이전트 + /orchestrate 명령"과 "고위험 변경의 교차검증을 위한 /cross-verify 스킬 추가"가 뒤따랐습니다. 계획하는 역할과 구현하는 역할, 검증하는 역할을 처음부터 분리해 둔 것인데, 이는 실제 팀을 꾸릴 때도 그대로 옮겨 쓸 수 있는 원칙입니다. 특히 위험도가 큰 결정일수록 검증 절차를 별도로 마련해 둔 점이 눈에 띕니다 — 사업에서도 계약, 채용, 큰 지출처럼 되돌리기 어려운 결정에는 이런 식의 "한 단계 더 확인하는 절차"를 미리 정해 두시길 권해 드립니다.

셋째, 시도했다가 과감히 되돌리는 것을 주저하지 않으셨습니다. 9월 13일 커밋을 순서대로 보면 "제갈량 스타일의 클로드 코드·사업 조언 메모리얼 페이지 추가" → "초원 사슴 삽화 추가" → "조언 페이지를 통합된 '사슴 대장' 초원 저널로 리디자인" → "손으로 그린 사슴 삽화 제거"로 이어집니다. 즉 콘셉트를 잡고, 요소를 더해 보고, 통째로 다시 디자인하고, 마음에 들지 않는 부분은 결국 빼내는 과정을 하루 안에 다 거치신 것입니다. 이건 실패가 아니라 정상적인 반복 작업입니다. 사업 아이디어나 제품 방향도 이렇게 "일단 만들어 보고, 다시 짜고, 안 맞는 건 빼는" 주기를 짧게 여러 번 도는 편이, 처음부터 완벽한 하나를 오래 붙잡고 있는 것보다 결과적으로 더 빨리 원하는 형태에 도달합니다. 다만 이런 반복이 가능했던 건 매번 git으로 기록을 남겨 두셨기 때문이라는 점도 함께 짚어드리고 싶습니다 — 되돌릴 수 있다는 안전망이 있어야 과감한 시도도 편해집니다.

넷째, 이 시스템을 다른 컴퓨터에서도 쓸 수 있게 만드셨습니다. "다른 컴퓨터에서 조언 팝업을 켤 수 있는 설치 스크립트 추가" 커밋이 그 증거입니다. 혼자 쓰는 도구를 한 대의 컴퓨터에만 묶어 두지 않고 이식 가능하게 만들어 두신 것인데, 이는 나중에 이 작업 방식을 다른 사람과 나누거나, 팀을 꾸려 넘겨줄 때도 훨씬 수월하게 만들어 주는 선택입니다. 사업에서도 "나만 아는 방식"으로 남겨두지 않고 문서화·스크립트화해 두는 습관이, 규모가 커질 때 병목을 크게 줄여 줍니다.

다섯째, 오늘(9월 14일) 하루 동안 이 보고서 자체를 세 번 넘게 고쳐 오셨습니다. "디자인된 ops-report 아티팩트와 docs/advice 미러 동기화" → "동기화·검증 개정 안내와 함께 R2로 업데이트" → "전체 대화 기록 기반 서술형 본문으로 R3 확장" 순서로 이어졌고, 마지막으로 "스케줄 에이전트가 매일 참고할 docs/advice/context.md 추가"가 오늘 가장 마지막 커밋으로 남아 있습니다. 이 마지막 커밋이 특히 중요합니다. 커밋 메시지에 직접 적혀 있듯, 클라우드에서 예약 실행되는 에이전트는 지금 이 대화의 맥락을 전혀 기억하지 못하기 때문에, 매일 반복되는 판단의 근거를 저장소 안의 파일 하나로 남겨 두기로 결정하신 것입니다. 이는 "사람이 매번 옆에서 설명해 주지 않아도 돌아가는 시스템"을 만드는 데 있어 핵심적인 통찰입니다. 사업을 키우실 때도, 대표님 한 분의 머릿속에만 있는 판단 기준은 그 사업의 성장 한계가 됩니다. 지금처럼 반복되는 결정의 근거를 문서 한 장으로 옮겨 두는 습관을, 사업의 다른 영역(가격 정책, 고객 응대 원칙, 채용 기준 등)에도 그대로 적용해 보시길 권해 드립니다.

여섯째, 그래서 오늘 드리고 싶은 구체적인 제안은 이렇습니다. docs/advice/context.md의 "현재 상황·최근 고민·최근 결정" 세 항목이 아직 비어 있습니다. 이 파일에 짧게라도 실제 사업 현황을 적어 두시면, 내일부터는 이 보고서의 Section B가 harness_test 저장소의 커밋 로그가 아니라 실제 사업 맥락을 근거로 훨씬 구체적인 조언을 드릴 수 있게 됩니다. 오늘 소프트웨어 쪽에서 실천하신 "판단 근거를 파일로 남겨서 반복 가능하게 만드는" 원칙을, 내일은 사업 쪽에도 딱 한 문단만 옮겨 적어 보시길 권해 드립니다.

일곱째, 안전장치를 먼저 만들고 나서 자동화를 넓혀 가는 순서도 그대로 참고할 만합니다. .claude/settings.json에는 git reset --hard, git push --force, git clean -f, rm -rf처럼 되돌리기 힘든 명령을 아예 차단 목록에 넣어 둔 채로, 그 위에 orchestrate 파이프라인과 매일 자동으로 갱신되는 이 보고서 같은 자동화를 쌓아 올리셨습니다. 순서가 중요합니다 — 먼저 "이 이상은 자동으로 넘어가지 않는다"는 선을 그어 두고 나서야 그 안쪽에서 자동화를 마음 놓고 넓힐 수 있는 것입니다. 사업을 자동화하거나 외부 도구·대행사·직원에게 위임을 넓혀 가실 때도 똑같은 순서를 권해 드립니다. 편의 기능부터 늘리지 마시고, 먼저 "이 금액 이상 지출, 이 문구가 들어간 계약, 이 범위를 넘는 고객 응대는 반드시 사람이 직접 본다"는 몇 가지 차단선부터 문서로 정해 두신 뒤에, 그 안에서 반복 업무를 하나씩 자동화해 나가시는 편이 훨씬 안전합니다.

여덟째, 완성도보다 "지금 진짜로 쓰고 있는가"를 기준으로 다음 할 일을 고르신 흔적도 보입니다. 사슴 삽화를 넣었다가 하루도 안 돼 빼신 것이나, 보고서를 R1에서 R2, R3를 거쳐 오늘 R4까지 계속 고쳐 오신 것 모두 "일단 완성해서 치워두는" 방식이 아니라 "실제로 매일 열어보면서 거슬리는 부분을 그때그때 고치는" 방식입니다. 이 방식의 장점은 쓸모없는 기능에 오래 매달리지 않는다는 점이고, 단점은 방향을 잃으면 계속 겉모습만 다듬게 될 수 있다는 점입니다. 그래서 오늘 이 시점에서 한 가지만 자문해 보시길 권해 드립니다 — 이 보고서 시스템을 매일 다듬는 시간이, 실제 사업을 앞으로 나아가게 하는 시간과 잘 이어지고 있는지 말입니다. 도구를 다듬는 재미와 사업을 키우는 일은 다른 종류의 노력이라, 가끔은 의식적으로 저울질해 보셔야 합니다.
